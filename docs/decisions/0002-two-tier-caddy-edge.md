# 0002. 엣지는 2단 Caddy

| 상태 | 채택 |
| --- | --- |
| 소관 | Member C (배포) |

## 맥락

호스트(OCI 144.24.90.88)에서 Carix 와 asset-pulse 두 프로젝트가 같이 돈다. 80/443 은 한
컨테이너만 바인딩할 수 있고 Let's Encrypt 는 그 두 포트로만 검증하러 온다. 초안은 단일
`nginx` 였다.

## 결정

**라우터 Caddy 한 단 + 프로젝트별 Caddy.** 라우터(`infra_caddy`, 저장소 밖 `~/infra`)가
80/443 과 TLS 종료·호스트명 분기를 소유하고, 프로젝트 Caddy(`carix_caddy`)가 애플리케이션
라우팅만 맡는다.

## 근거

- 포트를 나누면 한쪽 프로젝트가 정상 인증서를 못 받는다. 라우터를 한 단 두면 **모든
  프로젝트가 정상 TLS** 를 쓰면서 각자 자기 저장소에서 라우팅을 소유한다
- Caddy 는 인증서 자동 발급·갱신이 기본 동작이라 ACME 파이프라인을 직접 안 짠다
- 앱 라우팅 쪽은 Caddy 가 **업스트림을 요청마다 재해석**해 배포로 컨테이너 IP 가 바뀌어도
  영향이 없다. nginx 는 별도 우회가 필요하다

## 검토한 대안

- **단일 nginx** — 두 프로젝트 중 하나가 TLS 를 못 받는다
- **프로젝트마다 80/443 분할** — Let's Encrypt 검증이 안 된다

## 영향

- 라우터는 이 저장소가 배포하지 않는다. `~/infra` 는 git 미추적이고 참조용 사본만
  [`deploy/infra-edge/`](../../deploy/infra-edge/) 에 있다
- `carix_caddy` 는 git 관리 파일을 bind-mount 하므로 배포 시 `reload` 가 아니라
  `--force-recreate` 여야 한다 — inode 가 바뀌어 옛 파일을 계속 본다
