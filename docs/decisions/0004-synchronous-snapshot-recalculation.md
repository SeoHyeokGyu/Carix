# 0004. 스냅샷 재계산은 트랜잭션 안 동기 직접 호출

| 상태 | 채택 |
| --- | --- |
| 소관 | Member C (Job 4, `SnapshotRecalculationService`) |

## 맥락

사용자가 소득·소비·스킬·프로필을 바꾸면 그 시점 이후 월별 지수 스냅샷을 다시 써야 한다.
호출부가 여덟(소득 3 · 소비 1 · 스킬 3 · 프로필 1)이다.

## 결정

`recalculateSnapshot(userId, fromYm)` 을 **변경 트랜잭션 안에서 동기로 직접 호출**한다.
이벤트 발행 + `@Async` 는 택하지 않았다.

## 근거

- MVP 에서 **스레드풀·재시도·실패 관측 경로를 늘리지 않는다.** 비동기로 가면 그 셋이 함께
  따라온다
- 멱등성은 이미 `pg_advisory_xact_lock` 과 `data_version` 이 보증한다. 비동기가 풀어 줄
  문제가 없다
- 실패가 사용자 쓰기와 같은 트랜잭션에서 롤백되므로 스냅샷만 어긋난 상태가 안 생긴다

## 검토한 대안

- **도메인 이벤트 + `@Async`** — 응답은 빨라지지만 실패가 조용히 사라진다
- **메시지 브로커** — 서비스 넷 규모에 과하다 ([Spring Cloud 아키텍처 §9](../specs/spring-cloud-architecture.md))

## 영향

- 사용자 쓰기 응답 시간에 재계산이 포함된다. **실측으로 문제가 되면 그때 비관 이관한다** —
  그 이관안이 [아키텍처 로드맵 §4](../plans/architecture-roadmap.md) 다
- 운영 첫 쓰기에 `jsonb` 바인딩·자문 잠금·`MANDATORY` 전파가 동시에 처음 실행된다. 통합
  테스트가 H2 라 앞의 둘을 검증하지 못하므로 운영 검증 절차가 따로 있다
  ([문서 맵 「배포 전 실행 순서」](../README.md#남은-것))
