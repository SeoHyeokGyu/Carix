# 0001. 인증은 이메일·비밀번호 + 서버 세션

| 상태 | 채택 |
| --- | --- |
| 소관 | Member C (`auth-service`, 게이트웨이 세션 필터) |

## 맥락

초기 API 규격이 HTTP-only 쿠키, bearer `Authorization` 헤더, 상태ful `session` 테이블을
동시에 언급하며 우선순위와 포맷을 정하지 않았다. 클라이언트와 서버 구현이 갈릴 위험이
있었다. 별도로 초대 베타(10~30명) 전제의 매직링크·초대 코드 설계가 있었다.

## 결정

**서버 세션 단일 방식.** 이메일·비밀번호 계정으로만 가입·로그인하고, 불투명 토큰을
HTTP-only + Secure 쿠키에 담아 `session` 테이블에서 검증한다. 원본 토큰은 저장하지 않고
암호학적 해시만 저장한다. 매직링크·초대는 걷었다.

## 근거

- **즉시 폐기가 된다.** JWT 무상태 세션은 전체 로그아웃·강제 만료가 어렵다. 민감 재무
  데이터를 다루므로 토큰 유출 대응 경로가 단순해야 한다
- **세션은 30일짜리 자격증명**이라 DB 유출 시 피해가 가장 크다. 해시만 저장하면 유출된
  테이블로 세션을 되살릴 수 없다
- 매직링크·초대는 **이메일 발송 경로**를 요구한다. 사용자 실체가 본인과 방문자뿐이라
  초대 게이트가 지킬 대상이 없었고, 발송 인프라(`MAIL_*` 설정, 전송 실패 처리)만 남았다

## 검토한 대안

- **JWT 무상태 세션** — 즉시 폐기 한계로 배제
- **매직링크 + 초대 코드** — 초대 베타 전제가 사라지며 함께 폐기 (PR #105)

## 영향

- 비밀번호 재설정과 이메일 소유 증명은 MVP 범위 밖이다. 발송 수단이 없다
- 게이트웨이가 세션을 검증하고 `X-User-Id` 를 주입한다. core-api 는 Spring Security 대신
  그 헤더를 신뢰하고 없으면 401 이다
- 정책 상세는 [SECURITY §1](../SECURITY.md)
