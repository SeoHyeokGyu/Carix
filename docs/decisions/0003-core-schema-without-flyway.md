# 0003. `core` 스키마는 Flyway 를 쓰지 않는다

| 상태 | 채택 |
| --- | --- |
| 소관 | Member C (core-api), Member B (collector) |

## 맥락

`auth` 스키마는 `auth-service` 한 모듈이 소유하지만, `core` 스키마는 `collector`(채용공고
5테이블·`market_aggregate`)와 `core-api`(사용자 도메인·지수·시나리오)가 **공유**한다.
마이그레이션 도구를 쓰면 두 모듈 중 누가 버전 테이블을 소유하는지 정해야 한다.

## 결정

`auth` 스키마만 Flyway 로 관리한다. `core` 스키마는 [`deploy/postgres/schema/`](../../deploy/postgres/schema/)
의 `.sql` 파일을 직접 적용한다.

## 근거

공유 스키마에 마이그레이션 파일 관리 부담을 지우는 비용이 이득보다 크다고 봤다. 두 모듈이
같은 버전 테이블을 놓고 경쟁하거나, 한쪽이 다른 쪽 마이그레이션을 기다리는 배포 결합이
생긴다.

## 검토한 대안

- **`core` 도 Flyway** — 소유자 결정과 배포 결합 문제
- **모듈별 스키마 분리** — 지수 계산이 채용공고 집계를 조인해야 해서 스키마를 가르면 쿼리가
  깨진다

## 영향

- **적용 이력이 자동으로 안 남는다.** [ERD 「운영 스키마 적용 이력」](../specs/erd.md)이
  유일한 근거다. 운영 DDL 을 바꾸면 거기 한 줄을 남겨야 한다
- 운영 테이블에 행이 쌓인 뒤 컬럼을 더하면 수작업 마이그레이션이 붙는다 — `index_snapshot`
  OWI 컬럼(`c6`)을 첫 운영 쓰기 전에 넣기로 한 이유다
- 스키마를 가로지르는 외래키는 걸지 않는다. `users` 는 `auth` 소유라 `user_id UUID NOT NULL`
  만 두고 참조 무결성은 애플리케이션이 지킨다
