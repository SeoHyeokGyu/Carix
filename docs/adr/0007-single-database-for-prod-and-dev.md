# 0007. 운영과 개발이 같은 데이터베이스를 쓴다

- 상태: 채택
- 날짜: 2026-07-27
- 관련: [ADR 0003](0003-docker-db-oci-only.md)의 "운영 DB와 dev DB는 분리한다" 항목을 대체한다

## 맥락

초기 설계는 같은 Postgres 인스턴스 안에 `carix`(운영)와 `carix_dev`(개발) 두 DB를 두고
로컬 개발은 `carix_dev`에만 붙게 했다. initdb 스크립트가 `carix_dev` 롤·DB를 만들었다.

팀 프로젝트로 전환하면서 팀원들이 로컬에서 같은 데이터를 보며 개발할 필요가 생겼다.

## 결정

**DB를 하나만 둔다.** 운영과 개발이 모두 `carix`를 쓴다. 팀원은 SSH 터널로 이 DB에 붙는다.

- `carix_dev` DB·롤과 initdb 스크립트를 제거한다.
- 팀원은 **개인별 DB 롤**을 발급받는다. 공용 계정을 돌려쓰지 않는다 — 이탈 시 회수가 안 된다.

## 대안

- **DB 2개 분리 (이전 구성)** — 운영 데이터가 개발과 격리된다. 다만 개발 중 확인하고 싶은
  실제 데이터가 dev DB에 없어, 같은 데이터를 보려면 별도 동기화가 필요하다.
- **개발자별 로컬 DB** — 임베디드 Postgres 등으로 자격증명·충돌 문제가 사라지지만,
  팀이 같은 데이터를 공유하지 못한다.
- **관리형 dev DB(Neon 등) 브랜칭** — 브랜치별 격리를 얻지만 외부 서비스가 늘고
  운영과 버전 드리프트가 생긴다.
- **DBLab 자체 호스팅** — thin clone 으로 공유 데이터 + 격리를 동시에 얻는 정석이나,
  ZFS 가 필요하고 서버 디스크 여유가 25GB 뿐이라 이 호스트에는 과하다.

## 감수하는 위험

이 결정은 아래를 명시적으로 감수한다. 지금은 사용자와 데이터가 없어 실질 피해가 없으나,
**실데이터가 들어오는 시점 전에 재검토해야 한다.**

| 위험 | 내용 |
| --- | --- |
| 개인정보 접근 | 팀원 전원이 실사용자의 연봉·지출·경력 데이터에 직접 접근한다. `SECURITY.md`가 컬럼 암호화를 요구하는 그 데이터다 |
| 마이그레이션 사고 | 브랜치에서 잘못 실행한 Flyway 마이그레이션이 곧바로 운영 스키마에 적용된다 |
| 백업 부재 | 현재 DB 백업이 구현돼 있지 않다. 위 사고가 나면 복구 수단이 없다 |
| 테스트 데이터 혼입 | 로컬에서 만든 데이터가 운영 DB에 남는다 |
| 자격증명 확산 | 운영 DB 접근 정보가 팀원 노트북마다 존재한다 |
| 게이트 부재 | PR 단계 CI 와 자동 롤백이 없어(ADR 없음, 사용자 결정) 사고를 사전에 막거나 되돌릴 장치가 없다 |

## 결과

- 로컬 `.env`의 `SPRING_DATASOURCE_URL`은 `jdbc:postgresql://localhost:5432/carix`.
- 접근 절차와 개인별 롤 발급은 [`DEVELOPMENT.md`](../DEVELOPMENT.md) §3.0.
- Flyway 규약(타임스탬프 버전)은 같은 문서 §3.3. **공유 DB 시절보다 더 중요해졌다** —
  충돌이 운영 스키마에서 발생한다.
- **DB 백업이 최우선 후속 과제가 된다.** 위 위험표에서 유일하게 즉시 완화 가능한 항목이다.
- 서버에 남아 있는 기존 `carix_dev` DB·롤은 이 변경으로 자동 삭제되지 않는다
  (initdb 는 빈 볼륨에서만 실행된다). 수동 정리가 필요하다.
