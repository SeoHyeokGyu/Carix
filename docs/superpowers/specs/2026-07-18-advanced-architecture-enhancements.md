# Carix 아키텍처 고도화 및 성능 최적화 설계서 (Advanced Architecture Enhancements)

이 문서는 Carix 플랫폼이 프로덕션 환경에서 마주할 수 있는 쿼리 병목, 외부 시스템 장애, 비정형 데이터 정제 오차를 극복하기 위해 설계된 **시스템 아키텍처 고도화 방안 및 기술적 의사결정 사항**을 정의합니다.

---

## 1. 분산 캐싱 기반 데이터 조회 성능 최적화 (Distributed Caching)

### 1.1 배경 및 문제 정의
사용자의 시장가치 지수(MVI) 및 동료집단 통계 데이터는 다수의 공고 정보와 세부 필터를 동적으로 결합(Join/Group By)하는 무거운 집계 연산입니다. 대시보드 진입 시마다 관계형 데이터베이스(PostgreSQL)에 직접 쿼리를 수행할 경우, 동시 접속자가 늘어남에 따라 데이터베이스 CPU 병목과 API 지연 시간(Latency)이 기하급수적으로 증가합니다.

### 1.2 기술적 해결 방안
*   **다중 레이어 캐싱 (Multi-Level Caching):**
    *   배치 작업이 생성하는 스킬별/동료집단별 통계 데이터(`market_aggregate`)를 **Redis** 분산 캐시에 적재합니다.
    *   **Cache-Aside 패턴**을 사용하여 대시보드 조회 시 Redis에서 데이터를 우선 탐색하며, 캐시 미스(Cache Miss) 발생 시에만 RDB를 쿼리하고 캐시를 갱신합니다.
    *   Redis 적재 시 데이터 조회 속도를 향상하기 위해 **Redis Hash** 또는 **Redis JSON** 규격을 채택합니다.
*   **캐시 만료 및 일관성(Consistency) 정책:**
    *   배치가 주 1회 가동되므로 캐시의 기본 TTL(Time-To-Live)은 **8일**로 설정하여 데이터의 유효성을 보장하고, 배치가 성공적으로 완료되는 시점에 캐시를 강제 비우기(Evict) 처리하는 동기화 메커니즘을 적용합니다.

### 1.3 기대 효과 및 지표
*   **조회 지연 시간(Latency) 개선:** 평균 쿼리 응답 시간을 1.2초 대에서 **50ms 미만**으로 단축.
*   **DB 부하 경감:** 대시보드 메인 페이지 뷰의 Read 트래픽에 대한 RDB 의존성을 **90% 이상 차단**.

## 2. 형태소 분석 기반 비정형 스킬 키워드 추출 엔진 (NLP Skill Extraction)

### 2.1 배경 및 문제 정의
채용공고 본문은 작성자에 따라 "Spring Boot", "springboot", "스프링 부트", "스프링부트" 등 표기 방식이 달라 단순 문자열 매칭(Contains)만으로는 정확도와 재현율(Recall)이 저하됩니다. 또한 한국어 조사("Spring Boot는", "Spring Boot를")와 섞여 오탐지되는 문제를 최소화해야 합니다.

### 2.2 기술적 해결 방안
*   **형태소 분석기 및 토크나이저 연동:**
    *   Spring Batch의 전처리 단계에서 한국어 형태소 분석기(Elasticsearch Nori 토크나이저 플러그인 또는 온프레미스 파이썬 KoNLPy 어댑터 등)를 연동합니다.
    *   공고 본문에서 명사형 키워드와 영문 고유 명사를 추출(Tokenization)하고, 공백 및 특수문자를 제거해 정규화된 스킬 사전 테이블(`skill_alias`)의 값과 완전 일치 비교를 수행합니다.
*   **스킬 가중치 기반 필터링:**
    *   단순히 스킬 단어가 본문에 출현한 횟수뿐만 아니라, 공고 내 '우대사항', '자격요건' 영역의 텍스트 가중치를 다르게 주어 핵심 요구 스킬만 분류합니다.

### 2.3 기대 효과 및 지표
*   **데이터 신뢰성 향상:** 비정형 텍스트 스킬 매칭의 **정확도(Precision)와 재현율(Recall)을 95% 이상으로 유지**.
*   **정확한 데이터 확보:** 유사어 표기 차이로 인한 통계 왜곡 차단.

## 3. 서킷 브레이커 도입을 통한 서비스 회복 탄력성 확보 (Fault Tolerance)

### 3.1 배경 및 문제 정의
Carix의 실질 지표 연산에는 KOSIS 물가 지표와 고용24 OpenAPI 연동이 필수적입니다. 그러나 외부 정부 기관 API 서버는 간헐적인 시스템 점검, 응답 지연 또는 일시적 네트워크 장애가 잦습니다. 외부 서버의 응답 대기 지연이 해제되지 않으면 우리 서버의 API 스레드가 고갈되어 전체 서비스가 마비(장애 전파)되는 연쇄 장애를 유발할 수 있습니다.

### 3.2 기술적 해결 방안
*   **서킷 브레이커 패턴 도입:**
    *   **Resilience4j**를 외부 API 클라이언트 모듈(WebClient / FeignClient)에 적용합니다.
    *   외부 API 요청 실패율 또는 지연 시간 비율이 설정 임계치(예: 최근 20회 요청 중 50% 실패)를 초과할 경우, 즉시 서킷 브레이커를 Open 상태로 전환하여 외부 호출을 차단합니다.
*   **장애 극복(Fallback) 및 성능 저하 정책:**
    *   서킷 브레이커가 Open 혹은 Half-Open 상태일 때는 데이터베이스에 미리 복사된 **최신 성공 시점의 배치 데이터**를 즉시 반환하고 화면에 "데이터 업데이트 지연 (마지막 성공 기준일: YYYY-MM-DD)" 경고 배너를 표기하여 서비스 연속성을 유지합니다.

### 3.3 기대 효과 및 지표
*   **가용성 확보:** 외부 API 완전 마비 상태에서도 핵심 대시보드 서비스의 **가용성을 99.9% 이상 보장**.
*   **스레드 고갈 방지:** 응답 실패 대기 시간을 수십 초에서 **100ms 이내로 즉시 차단(Fail-Fast)**.

## 4. 이벤트 기반 비동기 아키텍처 구현 (Event-Driven Architecture)

### 4.1 배경 및 문제 정의
사용자가 프로필을 수정하거나 소득/소비 이력을 새로 업데이트하는 즉시 구매력 지수와 시장가치 지수의 재연산이 실행됩니다. 이를 사용자의 HTTP 요청 스레드에서 동기식(Synchronous)으로 끝까지 대기하여 처리하면 데이터베이스 쓰기/조회 연산이 겹치면서 API 응답 지연시간이 길어지고 사용자 경험을 해치게 됩니다.

### 4.2 기술적 해결 방안
*   **비동기 이벤트 리스너 활용:**
    *   `ProfileController` 및 `IncomeController`는 데이터 정합성을 검증한 후 DB 쓰기 연산을 마치고, 즉시 `ProfileUpdatedEvent` 또는 `IncomeUpdatedEvent` 이벤트를 발행(Publish)한 뒤 클라이언트에게 `200 OK` 응답을 리턴합니다.
    *   해당 이벤트는 Spring의 `@EventListener`와 **`@Async`** 어노테이션(또는 Redis Pub/Sub 메시지 브로커)을 사용하는 비동기 스레드 풀에서 캐치하여 지수 연산 및 스냅샷 저장을 비동기로 처리합니다.
*   **멱등성(Idempotency) 보장:**
    *   비동기 작업 실행 시 동일 월에 대한 스냅샷 갱신 요청이 중복 유입되더라도 `UPSERT` 쿼리를 통해 최종 상태가 안전하게 유입되도록 처리합니다.

### 4.3 기대 효과 및 지표
*   **사용자 체감 성능 개선:** 연산이 포함된 설정 수정 API의 응답 속도를 평균 **150ms 이내로 균일하게 단축**.
*   **시스템 결합도 완화:** 도메인 변경(소득/소비 입력)과 통계 엔진(지수/신호 산출) 간의 느슨한 결합 달성.
