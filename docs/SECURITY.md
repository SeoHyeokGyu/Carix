# Carix 보안·개인정보 처리

Carix는 연봉·실수령액·소비 금액 등 민감한 개인 재무 정보를 다룬다. 이 문서는 인증,
데이터 보호, 개인정보 수명주기 정책을 한곳에 모은다. 세부 규격은 각 설계 문서를
참조하되, 정책 기준은 이 문서를 따른다.

관련: [상세 기술 명세](specs/technical-specification.md),
[MVP 설계 §8](specs/mvp-requirements.md).

## 1. 인증

초기 API 규격은 HTTP-only 쿠키, bearer `Authorization` 헤더, 상태ful `session` 테이블을
동시에 언급하며 우선순위·포맷을 정하지 않아 클라이언트·서버 구현이 갈릴 위험이 있었다.
**서버 세션 단일 방식**으로 통일해 정리했다.

- 초대 기반 이메일 매직링크만 사용한다. 비밀번호 없음.
- 매직링크: 15분 유효, 1회 사용. 원본 토큰은 저장하지 않고 암호학적 해시만 저장한다.
  `magic_link_token.used_at`으로 재사용을 차단한다.
- 세션: 불투명 토큰을 HTTP-only + Secure 쿠키에 담고 서버 `session` 테이블에서
  검증한다. JWT·`Authorization` 헤더는 쓰지 않는다. 기본 유효기간 30일.
- 로그인 이메일은 초대 이메일과 정확히 일치해야 한다. 계정은 초대된 이메일의 첫
  매직링크 요청 시 생성한다.
- 개별 로그아웃과 전체 기기 로그아웃(전 세션 폐기)을 제공한다.

**JWT 무상태 세션은 검토 후 접었다** — 즉시 폐기(전체 로그아웃·강제 만료)가 어렵고,
민감 재무 데이터를 다루는 앱에서 토큰 유출 대응이 복잡해진다.

## 2. 계정 열거·남용 방지

- 초대되지 않은 이메일에도 동일한 발송 안내 응답을 반환한다.
- 매직링크 요청 속도 제한: 이메일당 5회/시간, IP당 20회/시간.

## 3. 저장 데이터 보호

### 3.1 컬럼 레벨 암호화

- 대상: `income_history.gross_salary_encrypted`, `income_history.net_salary_encrypted`,
  `expense_item.amount_encrypted`.
- 알고리즘: AES-256-GCM (또는 검증된 AES-256-CBC).
- 애플리케이션 레이어(Spring Data JPA `AttributeConverter`)에서 적재 시 암호화,
  조회 시 복호화한다. 평문은 DB 버퍼·파일시스템에 그대로 남기지 않는다.

### 3.2 키 관리 (구현 시 확정)

- 키는 `CARIX_ENCRYPTION_KEY` 환경변수로 주입한다. 저장소·로그에 커밋하지 않는다.
- 배치 워커도 스냅샷 계산 시 사용자별 연봉을 복호화한다. 배치 프로세스의 키 접근
  범위와 복호화 시점을 최소화한다.
- **미확정(구현 단계 처리):** 키 로테이션 절차와 로테이션 시 기존 암호문
  재암호화 전략. 배치 복호화 성능·키 접근 감사.

> **전환 예정.** 세션 검증이 Spring Cloud Gateway 필터로 이동한다. 하류 서비스는 세션을
> 모르고 `X-User-Id` 헤더만 신뢰하며, 그 전제는 Gateway 를 거치지 않으면 도달할 수 없는
> 네트워크 구성이다 ([Spring Cloud 아키텍처](specs/spring-cloud-architecture.md)).

### 3.3 전송·인프라

- 모든 통신은 HTTPS. 서버의 라우터 Caddy(`infra_caddy`)에서 TLS 종료하며 인증서는
  sslip.io + 자동 ACME로 발급·갱신한다. 프로젝트 전용 `carix_caddy`는 `auto_https off`로
  내부 평문 :80만 받고 인증서를 다루지 않는다. **인증서 관리 지점을 하나로 모으기 위한 구조**이며,
  공유 호스트에서 80/443을 한 컨테이너만 바인딩할 수 있다는 제약에서 나왔다.
- 운영 DB는 OCI VM PostgreSQL 컨테이너로 운영하며 볼륨 암호화, 일일 자동 백업과
  복구 절차 검증, 이미지 버전 고정을 함께 한다(서버 전용 근거는 README.md 채택 사유).
- **운영과 개발이 같은 DB를 쓴다.** 따라서 팀원은 실사용자 데이터에 직접 접근한다.
  감수한 위험과 재검토 시점은 [`DEVELOPMENT.md`](DEVELOPMENT.md) §3 참조.
- 접근 경로는 **Headscale**(자체 호스팅 Tailscale)이다. DB 포트는 `127.0.0.1`에만 바인딩하고
  호스트의 `tailscale serve`가 tailnet 내부로만 중계한다. 인터넷 노출은 없고 구간은
  WireGuard로 암호화된다.
- 신원은 Headscale preauth key로 등록하고, DB 인증은 **개인별 롤**을 쓴다. 공용 계정을
  돌려쓰지 않는다 — 이탈 시 회수가 불가능하다 ([DEVELOPMENT.md §3.0](DEVELOPMENT.md)).
- 팀원이 빠지면 Headscale 사용자와 DB 롤을 함께 제거한다.
- **`headscale-data` 볼륨은 백업 대상이다.** 노드 키와 ACL을 담고 있어 잃으면 팀원 전원이
  재인증해야 한다.
- **DB 백업이 아직 구현돼 있지 않다.** 운영 DB를 개발에 함께 쓰는 구성에서는 마이그레이션
  사고가 곧 운영 데이터 손실이므로, 실데이터 유입 전 최우선으로 갖춘다.
- **PostgreSQL은 인터넷에 노출하지 않는다.** 컨테이너 포트를 `127.0.0.1`에만 바인딩하고
  로컬 개발은 Headscale tailnet 으로 접근한다. 현재 Postgres는 TLS가 꺼져 있어 직접 노출하면 자격증명과
  쿼리·결과가 평문으로 오간다. Docker가 발행한 포트는 호스트 방화벽(firewalld)을 우회하므로,
  실수로 `0.0.0.0`에 바인딩하면 OCI Security List 외에는 막을 수단이 없다.

## 4. 로그·관측성에서의 민감정보 배제

- 연봉·실수령액·소비 금액을 애플리케이션 로그·분석 이벤트에 남기지 않는다.
- 작업 전달·로그에는 이메일 대신 내부 사용자 ID를 사용한다.
- 로그에는 요청 ID와 오류 코드만 남기고 민감 입력을 제외한다.
- 오류 응답에 내부 코드·스택·내부 URL을 노출하지 않는다.
- MVP 운영 도구에서 사용자별 민감 금액을 조회하지 않는다.

## 5. 개인정보 수명주기

- 최소 수집: 지수 계산에 필요한 범위만 수집한다.
- 사용자 및 개인 데이터 삭제 시 프로필, 개인 입력 이력(소득·소비·스킬), 스냅샷, 시나리오, 세션,
  그리고 동일 이메일의 초대 기록을 삭제한다. 삭제 전 범위를 고지하고 이메일 재입력
  으로 확인받는다.
- 공용 CPI·채용시장 집계 데이터는 개인 데이터와 논리적으로 분리하며, 집계에 사용자
  이메일을 포함하지 않는다. 사용자 정보 삭제는 공용 집계에 영향을 주지 않는다.
- 외부 원문(`raw_ingest`) 보존은 24개월이며 초과분은 원문만 삭제하고 메타데이터를
  유지한다.

## 6. 입력 검증

- 시스템 경계에서 모든 사용자 입력을 검증한다. 허용 범위는
  [기능 분해 명세 §3](specs/functional-specification.md)을 따른다.
- 음수·범위 초과 금액, 미래 시점 이력, 중복 유효일 소득, 중복 스킬을 거부한다.
- 파라미터화 쿼리·ORM으로 SQL 인젝션을 방지하고, 프런트엔드 출력은 이스케이프한다.

## 7. 취약점 신고

저장소가 PRIVATE인 동안은 협업자가 이슈로 보고한다. 공개 전환 시 신고 채널과
대응 정책을 이 절에 확정한다.
